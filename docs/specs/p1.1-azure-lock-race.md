> ## ⚠️ VERIFICATION CORRECTION (2026-06-27) — VALID, WITH ONE WRONG SUB-CLAIM
>
> The core finding is **valid**: the constructor fires `createContainerIfNotExists` fire-and-forget (no readiness gate), and the
> callback swallows the error (`//TODO: log`, `:18`). The proposed `ready` gate + logging is a sound fix. **But two details in the
> draft are inaccurate:**
> 1. The code snippet in §1 below omits line 19. The real callback is **not** empty — it contains
>    `self.renewTimer = setInterval(this.renewLeases, 45000, self);`.
> 2. The related claim (carried from the plan) that *"the renew timer never starts on container-creation failure"* is **false** —
>    that `setInterval` runs **unconditionally inside the callback**, so it currently starts on success *and* on error. The genuine
>    improvement (correctly reflected in the §5 proposed code) is to start the timer **only on success** and resolve `ready=false`
>    on error. Rule §6.4 is reworded accordingly. Severity unchanged (HIGH).

## 1. Context (self-contained)

### Bug site: `azure-lock-manager.ts` constructor

```typescript
// providers/workflow-es-azure/src/azure-lock-manager.ts:14-21 (actual current code)
constructor(connectionString: string) {
    var self = this;
    this.blobService = createBlobService(connectionString);
    this.blobService.createContainerIfNotExists(this.containerId, (error, result, response) => {
        //TODO: log
        self.renewTimer = setInterval(this.renewLeases, 45000, self);  // ← starts on success AND on error today
    });    
}
```

Two problems:
1. **Race**: Container creation is async fire-and-forget. If `acquireLock()` is called before the container exists, it fails silently with no diagnostic.
2. **Error swallowed**: The callback ignores its `error` parameter (`//TODO: log`). If container creation fails (access denied, network unreachable), all subsequent operations silently fail without any indication of root cause.

### Consequence

In a deployment where the Azure storage account is misconfigured or access is revoked, the lock manager appears to work (constructor returns successfully) but all `acquireLock` calls return `false` silently. The poll worker never gets the lease, no instances are queued, and there is zero indication of what went wrong.

---

## 2. Goal

Add a `ready: Promise<boolean>` field on `AzureLockManager` that resolves when container creation completes (or errors). Add error logging to the callback. Gate all public methods behind the ready check — reject or return failure with a meaningful message if not ready.

## 5. Interface & data-model changes

### New field on class (Azure-specific)

```typescript
// azure-lock-manager.ts
private readyPromise: Promise<boolean>;
private isReady: boolean = false;

constructor(connectionString: string) {
    this.blobService = createBlobService(connectionString);
    
    this.readyPromise = new Promise<boolean>((resolve) => {
        this.blobService.createContainerIfNotExists(
            this.containerId, 
            (error, result, response) => {
                if (error) {
                    // Log at warn level — the container may already exist or be inaccessible
                    console.warn(`[AzureLockManager] Failed to create container '${this.containerId}': ${error.message || error}`);
                    this.isReady = false;
                    resolve(false);
                } else {
                    console.info(`[AzureLockManager] Container '${this.containerId}' ready`);
                    this.isReady = true;
                    this.renewTimer = setInterval(this.renewLeases, 45000, this);
                    if (this.renewTimer && typeof this.renewTimer.unref === 'function') {
                        this.renewTimer.unref();
                    }
                    resolve(true);
                }
            }
        );
    });
}

// New public getter (Azure-specific)
public get ready(): Promise<boolean> {
    return this.readyPromise;
}
```

### All public methods — add readiness check

```typescript
private assertReady() {
    if (!this.isReady) {
        throw new Error('AzureLockManager is not ready — container creation failed or pending');
    }
}

// In acquireLock, releaseLock: call this.assertReady() at the start
```

### DI / config impact

None. The `ready` getter is Azure-specific and not part of the shared interface. Consumers should await it before using the lock manager in production (the single-node provider already handles this via its `markStarted` pattern).

### Persisted / at-rest format impact

None.

## 6. Behavioural contract (numbered rules)

1. The constructor must create a `readyPromise` that resolves to `true` on success or `false` on error — callers can await it before using the lock manager in production deployments.
2. The container creation callback must log the error at warn level if creation fails; never silently swallow it.
3. If `isReady === false`, public methods (`acquireLock`, `releaseLock`) must throw a descriptive error rather than silently returning failure. This makes the failure visible immediately during testing/initialization.
4. The renew timer is *already* started inside the callback, but today it starts on **both** success and error. After this fix it
   must start **only on success** (in the `else` branch); on error, `ready` resolves `false` and no timer is armed.

## 12. Implementation notes (optional, non-binding)

The simplest implementation: add the `readyPromise` + error log in the constructor. For the public method guard, use a soft approach — return `false` with a logged warn if not ready, rather than throwing, to avoid breaking existing callers. The throw option is more aggressive but catches initialization errors earlier. I recommend throwing for clarity.
