## 1. Context (self-contained)

### The bug

In `core/src/services/workflow-executor.ts`, the method `determineNextExecutionTime` (line ~315) contains this pattern:

```typescript
// workflow-executor.ts, lines 315-326
if ((instance.nextExecution === null)) {            
    for (let pointer of instance.executionPointers.filter(x => x.active && x.children.length > 0)) {
        if (!instance.executionPointers.filter(x => x.scope.includes(pointer.id)).every(x => !!x.endTime)) 
            continue;
        
        if (!pointer.sleepUntil) {
            instance.nextExecution = 0;
            return;
        }
        instance.nextExecution = Math.min(pointer.sleepUntil, instance.nextExecution ? instance.nextExecution : pointer.sleepUntil);
    }            
}
```

When the filter on line 318 finds no pointers in `pointer.scope`, `[].every(fn)` returns `true`. The negation produces `false`, so the body **executes** even though there are zero children. In normal single-path workflows where most pointers have empty scopes, this means:
- The code enters the loop body unnecessarily
- It compares `sleepUntil` values against an effectively-zero child set
- It may incorrectly set `nextExecution = 0` or a stale timestamp

### Root cause

`[].every(fn) === true` is standard JavaScript (vacuous truth). The filter returning zero items does **not** mean "all children have ended" — it means "there are no children to check."

---

## 2. Goal

Fix the empty-set semantics so that when a pointer has no children in its scope, the code correctly recognizes this and either skips or handles it appropriately. The fix should use `.some()` with negated logic instead of `.every()`, or add an explicit guard for the zero-item case.

## 6. Behavioural contract (numbered rules)

1. When `executionPointers.filter(x => x.scope.includes(pointer.id))` returns zero items, the code must **not** execute the loop body based on vacuous truth — it must recognize "no children in scope" as a distinct case from "all children have ended."
2. The recommended fix is to replace `.every()` with `.some()` and negate: `!filter(...).some(fn)` reads "no items match" rather than "all items match (vacuously true)."
3. Alternatively, add an explicit `if (children.length === 0) continue;` guard before the `.every()` call.

## 12. Implementation notes (optional, non-binding)

The safest fix is to add an explicit guard:
```typescript
const scopeChildren = instance.executionPointers.filter(x => x.scope.includes(pointer.id));
if (scopeChildren.length === 0) continue;
if (!scopeChildren.every(x => !!x.endTime)) continue;
```
This is clearer than negating `.some()` and makes the intent explicit. The variable name `scopeChildren` documents what the filter selects.
