> ## ✓ VERIFICATION NOTE (2026-06-27) — VALID, but the host has no `shuttingDown` field yet
>
> Confirmed: `//todo: check host status` at `workflow-host.ts:194`, and `publishEvent` performs no host-state check.
> **Important correction:** the draft below assumes `stop()` "sets `shuttingDown = true`" and that the guard can read
> `this.shuttingDown`. **`WorkflowHost` has no such field** — it only has `stopPromise` (set in `stop()`/`performStop()`,
> reset to `null` in `start()`). The `shuttingDown` booleans live on the *worker* classes (`PollWorker`, `EventQueueWorker`) and
> are not visible from the host. So the fix must **introduce** the flag:
> - add `private shuttingDown = false;`, set it `true` at the top of `performStop()`, reset it to `false` in `start()`; **or**
> - guard on the existing state with `if (this.stopPromise) { … }`.
> Everything else in this spec (log-and-return, non-breaking `Promise<void>`) is correct.

## 1. Context (self-contained)

### The bug

In `core/src/services/workflow-host.ts:publishEvent`:

```typescript
// workflow-host.ts, lines ~193-218
public async publishEvent(eventName: string, eventKey: string, eventData: any, eventTime: Date, tenantId: string = DEFAULT_TENANT): Promise<void> {
    //todo: check host status  ← UNREACHABLE / UNUSED

    this.logger.log(LogLevel.Info, "Publishing event", { eventName, eventKey });

    let evt = new Event();
    evt.tenantId = tenantId || DEFAULT_TENANT;
    evt.eventData = eventData;
    evt.eventKey = eventKey;
    evt.eventTime = eventTime;
    evt.isProcessed = false;
    await this.codecRunner.encodeEvent(evt);
    let id = await this.persistence.createEvent(evt);
    // ... metrics ...
    this.queueProvider.queueForProcessing(id, QueueType.Event);
}
```

The `//todo: check host status` comment indicates an intention that was never implemented. Events are published to persistence and queued **even after** `stop()` is called on the host. (Note: `stop()`/`performStop()` today only set `stopPromise` — there is no `shuttingDown` flag on the host yet; see the correction box.) This means:

1. Event accumulation: On a stopped host, new events pile up in the persistence store with zero processing happening.
2. Silent failure: The caller has no indication that the event was published to a stopped host — the call succeeds but nothing happens.
3. Queue exhaustion: In long-running deployments where `publishEvent` continues being called after shutdown, the queue could grow unbounded (events waiting for a worker that will never process them).

---

## 2. Goal

Replace the TODO comment with an actual check: `publishEvent` should refuse to publish new events when the host is shutting down or stopped. Log a warning and return early (or throw) to make the failure visible to callers.

**Recommendation**: Return a `boolean` (success/failure) or add a guard that throws when shutting down — making the failure explicit rather than silently accepting work that will never be processed.

## 5. Interface & data-model changes

### Approach A (non-breaking): log warning + return early (recommended)

```typescript
// BEFORE:
public async publishEvent(eventName: string, eventKey: string, eventData: any, eventTime: Date, tenantId: string = DEFAULT_TENANT): Promise<void> {
    //todo: check host status
    // ... rest of method ...
}

// AFTER:
public async publishEvent(eventName: string, eventKey: string, eventData: any, eventTime: Date, tenantId: string = DEFAULT_TENANT): Promise<void> {
    if (this.shuttingDown) {
        this.logger.log(LogLevel.Warn, "Cannot publish event — host is shutting down", { eventName, eventKey });
        return;
    }
    // ... rest of method unchanged ...
}
```

### Approach B (breaking but explicit): throw on shutdown

```typescript
if (this.shuttingDown) {
    throw new Error("Cannot publish event — host is stopped");
}
```

**Recommendation**: Use Approach A (non-breaking). The `IWorkflowHost` interface returns `Promise<void>`; changing the return type to `Promise<boolean>` or `Result<...>` would be a breaking change requiring version bump and consumer updates. A logged warning + early return is sufficient — it makes the failure visible in logs without forcing consumer changes.

### DI / config impact

None.

### Persisted / at-rest format impact

None.
