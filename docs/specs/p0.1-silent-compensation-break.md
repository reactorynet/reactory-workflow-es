## 1. Context (self-contained)

In `core/src/services/execution-result-processor.ts`, two methods contain a bug where a method is accessed as a property instead of invoked:

### Bug site 1 — `shouldCompensate` (line 257)

```typescript
// execution-result-processor.ts:257
if (step.revertChildrenAfterCompensation)
    return true;
```

This reads the *function reference* on `SagaContainer.revertChildrenAfterCompensation`. A function reference is always truthy, so this condition **always** evaluates to `true` regardless of what the step's logic actually intends. Every saga step with a non-null `compensationStepId` will trigger compensation logic unconditionally.

### Bug site 2 — `compensate` (line 196)

```typescript
// execution-result-processor.ts:196
if ((!parentStep.resumeChildrenAfterCompensation()) || (parentStep.revertChildrenAfterCompensation())) {
    resume = parentStep.resumeChildrenAfterCompensation();
    revert = parentStep.revertChildrenAfterCompensation();
}
```

Same pattern: `parentStep.revertChildrenAfterCompensation` is accessed as a property (always truthy). Both branches of the `||` condition evaluate using the parent's values unconditionally — the conditional branching logic is completely bypassed.

The root cause is that `SagaContainer` (core/src/models/saga-container.ts) defines these as methods:
```typescript
public revertChildrenAfterCompensation(): boolean { return true; }
public resumeChildrenAfterCompensation(): boolean { return false; }
```
But the callers read them without `()`.

### User-visible impact

Saga compensation runs when it shouldn't, or uses wrong values for `resume`/`revert`. This silently breaks saga semantics — steps that should not be compensated get compensated (or vice versa), and compensation order is incorrect. The saga-compensation.spec.ts characterization test likely asserts incorrect values as a result.

---

## 2. Goal

Add `()` to both callsites so the methods are properly invoked, producing correct conditional branching based on each step's actual intent.

## 6. Behavioural contract (numbered rules)

1. `shouldCompensate` must call `step.revertChildrenAfterCompensation()` (with parentheses) — the return value determines whether compensation should trigger, not the mere existence of the method.
2. `compensate` must call both `parentStep.resumeChildrenAfterCompensation()` and `parentStep.revertChildrenAfterCompensation()` (with parentheses) — the conditional branching logic in lines 196–199 depends on actual return values, not truthiness of function references.
3. The fix is a one-character insertion at two call sites: adding `()` after each method reference.
4. No behavioral contract changes to other methods.
