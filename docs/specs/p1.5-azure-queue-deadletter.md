## 1. Context (self-contained)

### The bug

In `providers/workflow-es-azure/src/azure-queue-provider.ts`, messages are deleted immediately upon receipt:

```typescript
// azure-queue-provider.ts
self.queueService.getMessage(queueName, (error, result, response) => {
    if (!result) resolve(null);
    else {
        self.queueService.deleteMessage(...); // fire-and-forget
        resolve(result.messageText);
    }
});
```

If the processing node crashes between message receipt and successful workflow processing, the message is **permanently lost**. The Redis queue provider (`redis-queue-provider.ts`) mitigates this using `rpoplpush` (a pending queue pattern), but the Azure provider has no equivalent.

### Impact

Workflow IDs are silently lost on crash. A node processes 10 workflows and crashes after processing 3 — the remaining 7 workflow IDs are gone forever from the queue. They will never be re-executed, meaning in-flight workflows stall indefinitely.

---

## 2. Goal

Add a visibility timeout to Azure queue message retrieval so messages remain invisible (not visible to other workers) while being processed. If processing completes successfully, delete the message. If the node crashes before deleting, the message becomes visible again after the visibility timeout expires and is re-queued for processing. This mirrors the Redis provider's pending queue semantics using Azure Storage Queues' built-in visibility timeout feature.

---

## 3. Out of scope

- Changes to any other queue provider (Redis, single-node).
- Changes to `IQueueProvider` interface (no new methods — use Azure's built-in visibility timeout).
- Dead-letter queue for poisoned messages (out of scope; this is a pending queue, not a DLQ).
- Any changes outside `providers/workflow-es-azure/src/azure-queue-provider.ts`.

## 5. Interface & data-model changes

None. This uses Azure Storage Queues' built-in visibility timeout feature — no interface changes needed.

### Visibility timeout configuration

Add a configurable visibility timeout (default: 60 seconds, matching the Redis pending queue default):

```typescript
// azure-queue-provider.ts class fields
private visibilityTimeoutMs: number = 60000; // ms messages are invisible while being processed
```

This can be passed via constructor options or configured at host start.

### DI / config impact

No new `TYPES` binding needed. The visibility timeout is a simple numeric config — pass via the provider's constructor options (same pattern as existing Azure queue provider).

### Persisted / at-rest format impact

None. No on-disk format change.

---

## 6. Behavioural contract (numbered rules)

1. `dequeueForProcessing` must call `getMessage` with a visibility timeout — the message becomes invisible to other workers for the duration.
2. On successful workflow processing, the message is deleted normally.
3. If the node crashes before deletion, the message becomes visible again after the visibility timeout and is re-queued (same as Redis provider's pending queue behavior).
4. The visibility timeout should be configurable (default 60s) via constructor options or host configuration.

## 11. Definition of Done

The timeout is configurable with a sensible default. Build passes and tests verify both happy-path deletion and crash-recovery visibility.

## 12. Implementation notes (optional, non-existing)

Azure Storage Queues `getMessage` accepts a `visibilityTimeout` parameter. Use the `queueService.getMessage` callback API (matching existing code style):

```typescript
self.queueService.getMessage(queueName, { visibilityTimeout: timeoutMs }, (error, result, response) => {
    // ... existing logic
});
```

The visibility timeout should be applied consistently on both `dequeueForProcessing` calls. No changes to `queueForProcessing` (enqueue path is unaffected).
