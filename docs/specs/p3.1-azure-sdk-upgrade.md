>
> The finding is valid (deprecated SDK), but: (1) `package.json` pins `azure-storage` at **`^2.10.7`** — i.e. **v2.x** (the
> package's final release), **not** "v1.x"; (2) there is **no single `@azure/storage-blob + @azure/storage-queue` package**. The replacement is two
> modular SDKs: **`@azure/storage-blob`** for the lock manager (it leases **blobs**) and **`@azure/storage-queue`** (singular) for
> the queue provider. "Known unpatched vulnerabilities" is unverified — rest the case on "deprecated/unmaintained, no modern auth."

## 1. Context (self-contained)

### The problem

Both Azure files import from the deprecated legacy `azure-storage` package (named imports, not a namespace import):

```typescript
// azure-lock-manager.ts:2
import { BlobService, createBlobServiceWithSas, createBlobService, ErrorOrResult, ErrorOrResponse, ServiceResponse } from "azure-storage";
// azure-queue-provider.ts:2
import { QueueService, createQueueService, ErrorOrResult, ErrorOrResponse, ServiceResponse } from "azure-storage";
```

This package (pinned at `^2.10.7`):
- Is **deprecated/unmaintained** — Microsoft superseded it with the modular `@azure/storage-*` SDKs (v12+)
- Does not support modern Azure AD authentication or managed identities
- Uses callback-style APIs (not async/await)

### Decision tree

**Option A: Migrate to `@azure/storage-blob + @azure/storage-queue` (v12+)**
- Requires rewriting both lock and queue providers to use the new SDK's async APIs
- Supports Azure AD authentication, managed identities, and all modern Azure features
- Larger change but long-term sustainable

**Option B: Deprecate the Azure provider entirely**
- If Azure is not a supported or required platform for this codebase
- Add README banner deprecating the provider with migration guidance to Redis or PostgreSQL alternatives

### Recommendation

**Start with Option B (decision first)** — review whether Azure support is actually required by the project. If yes, migrate (Option A) as a separate item. If no, deprecate and remove from CI. This spec covers **both paths**.

## 10. Backward compatibility & migration

If deprecated: existing consumers must migrate away before this provider package is removed. Document a timeline and provide a no-op stub that logs deprecation warnings.

If migrating: breaking change to constructor parameters (authentication pattern). Requires version bump to minor pre-release (`2.4.0-reactory.N`). Consumers update their initialization code per the README migration guide.

## 11. Definition of Done

A decision is made and documented: either deprecation with clear migration guidance, or migration to `@azure/storage-blob + @azure/storage-queue` v12+ with working integration tests. CI matrix reflects the decision. The roadmap table in this plan is updated.

---

## 12. Implementation notes (optional, non-binding)

Key considerations for the decision:
- Does any consumer (`reactory-express-server`, Electron samples) actually use the Azure provider? If no, deprecate immediately.
- Is Azure a strategic platform for the product? If yes, invest in migration to `@azure/storage-blob + @azure/storage-queue`.
- The migration to `@azure/storage-blob + @azure/storage-queue` involves replacing callback-based `queueService.getMessage/putMessage/deleteMessage` with async/await `QueueClient.getMessage/peekMessages/sendMessage` and similar lock operations.
