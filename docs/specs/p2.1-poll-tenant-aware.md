## 1. Context (self-contained)

### The issue

In `core/src/services/poll-worker.ts:processInner`:

```typescript
// poll-worker.ts, line ~138
let events = await self.persistence.getRunnableEvents();
for (let item of events) {
    self.queueProvider.queueForProcessing(item, QueueType.Event);
}
```

`getRunnableEvents()` without a tenantId returns events across **all tenants** (per the persistence contract). The poll worker then queues all these event IDs onto the queue without tenant scoping. While the subscription seed in `event-queue-worker.ts` eventually checks tenant isolation, there is a window where:
1. Events from multiple tenants are queued indiscriminately
2. If two tenants' events arrive out of order on the queue, they may be processed before per-event locks serialize them
3. The poll worker has no mechanism to prefer tenant-specific scanning

### Impact

In a multi-tenant deployment, this is primarily an ordering concern rather than a correctness issue (per-event locks prevent actual data corruption). However, it creates unnecessary processing load on the queue and can cause confusing event interleaving in logs. It also violates the principle that tenant scoping should be enforced at every layer of the pipeline, not just the final subscriber.

---

## 2. Goal

The poll worker's `getRunnableEvents()` call should either:
(a) Accept an optional tenantId and iterate known tenants (same pattern as `getRunnableInstances`), or
(b) Rely on the persistence layer to return tenant-scoped results when a default tenant context is set, or
(c) Be documented as acceptable with the note that per-event locks provide the final isolation guarantee.

Given that the poll worker's queue-only responsibility is lightweight, option (c) with documentation is the simplest and safest change. The `getRunnableInstances` path already has tenant support in the persistence layer; events follow the same pattern. No behavioral change to the persistence interface or contract is required.

**Recommendation**: Document the acceptable behavior but add a comment clarifying that tenant isolation is enforced at the subscription seed layer, not at poll time. Consider adding a future optional `getRunnableEvents(tenantId?)` parameter if multi-tenant polling optimization becomes necessary.

## 12. Implementation notes (optional, non-binding)

If the reviewer wants a more substantive fix than documentation, consider:
- Adding `getRunnableEvents(tenantId?: string)` to `IPersistenceProvider` with backward-compatible default.
- Poll worker iterates known tenants or uses a default tenant context.

However, given that per-event locks provide correctness and this is primarily an ordering concern (not a data integrity issue), documentation is the recommended approach for this item. The persistence layer already supports tenant-scoped event polling — adding it to the poll worker can be deferred as a separate optimization.
