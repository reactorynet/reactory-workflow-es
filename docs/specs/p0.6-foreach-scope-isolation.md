## 1. Context (self-contained)

### What the engine does today

`Foreach` fans out its whole collection in one `ExecutionResult.branch(...)`
(`core/src/primitives/foreach.ts:14`):

```ts
if (!context.persistenceData) {
    let containerData = new ContainerData();
    containerData.childrenActive = true;
    return ExecutionResult.branch(this.collection, containerData);
}
```

`ExecutionResultProcessor` turns each branch value into one child `ExecutionPointer` per child step
(`core/src/services/execution-result-processor.ts:70-76`), and `ExecutionPointerFactory` stamps the
branch value onto the pointer (`core/src/services/execution-pointer-factory.ts:40`):

```ts
result.contextItem = branch;
```

`buildNextPointer` then propagates `contextItem` to each successor pointer within the body
(`execution-pointer-factory.ts:26`). **So the per-iteration item is tracked correctly, and it is
correctly carried down the body chain.** That part works.

### Where it breaks

`WorkflowExecutor` makes the item available to the step body, but **not to the input/output
mappers**. From `core/src/services/workflow-executor.ts`:

```ts
79:    stepContext.item = pointer.contextItem;          // ✅ body.run(context) can see the item
...
85:    for (let input of step.inputs) {
86:        input(body, instance.data);                   // ❌ no pointer, no item
87:    }
...
127:   for (let output of step.outputs) {
128:       output(body, instance.data);                  // ❌ writes to ONE shared object
129:   }
```

The mapper contract itself has only two parameters
(`core/src/models/workflow-step.ts:23-24`):

```ts
public inputs:  Array<(step: StepBody, data: any) => void> = [];
public outputs: Array<(step: StepBody, data: any) => void> = [];
```

exposed publicly as (`core/src/fluent-builders/step-builder.ts:81,86`):

```ts
public input (expression: (step: TStepBody, data: TData) => void): StepBuilder<TStepBody, TData>
public output(expression: (step: TStepBody, data: TData) => void): StepBuilder<TStepBody, TData>
```

Three consequences, all silent — no exception, no warning, wrong results:

**(a) Control-flow predicates inside a foreach body cannot see the current item.**
`.if()`, `.while()` and a nested `.foreach()` all bind their expression against `data` only
(`step-builder.ts:173`, `:158`, `:143` respectively):

```ts
newStep.inputs.push((step: If, data: any) => step.condition = expression(data));
```

`data` is `instance.data` — the workflow-wide object. A predicate such as "skip this row if
`item.status === 'archived'`" is **not expressible**. Neither is a nested foreach over a collection
derived from the outer item (`order.lines`), which is the single most common nested-iteration shape.

**(b) `.output()` from N iterations races into one slot.** Every branch writes to the same
`instance.data`. With a multi-step body the executor advances pointers in **lockstep, breadth-first**
— `exePointers` is snapshotted once per pass (`workflow-executor.ts:39`) and every currently-active
pointer runs in that pass:

```ts
let exePointers: Array<ExecutionPointer> = instance.executionPointers.filter(x => x.active);
```

So pass *k* runs step-1-of-every-item, pass *k+1* runs step-2-of-every-item. By the time step 2 of
item #1 executes, all N copies of step 1 have already written to `instance.data` and only the last
writer survives. **Step 2 of item #1 reads item #N's output.**

**(c) The defect is invisible for single-step bodies.** `.foreach().do(then => then.startWith(X))`
behaves correctly, which is exactly the shape of every foreach test and sample in the repo. The
corruption only appears once a body has two or more steps that pass data between them — i.e. as soon
as a foreach does real work.

### User-visible impact

A workflow author writes the obvious thing:

```ts
.foreach(data => data.orders)
 .do(then => then
     .startWith(FetchOrderDetail).output((s, d) => d.detail = s.result)
     .then(ChargeCard).input((s, d) => s.amount = d.detail.total))
```

Every card is charged the **last** order's amount. No error is raised. On a compensating (saga)
body, the compensation reads the same corrupted slot. This is a correctness bug with a plausible
path to financial and data-integrity harm, and it is undetectable from logs.

### Provenance

This behaviour is **inherited from upstream `danielgerlag/workflow-es`**, not introduced by this
fork. Upstream's own foreach samples are all single-step, which is why it was never surfaced. It is
recorded here because the fork's consumers (notably the YamlFlow compiler in
`reactory-express-server`) generate multi-step foreach bodies as a matter of course.

### Downstream consumer note (context only — not in scope)

`reactory-express-server`'s YamlFlow layer compiles `for_each` onto this primitive
(`src/modules/reactory-core/workflow/YamlFlow/YamlFlowBuilder.ts`) and additionally records step
results in a step-id-keyed map (`data.stepResults[def.id]`), which collides for the same reason. That
is a **separate fix in that repository** and is tracked there. It cannot be fixed correctly until
this engine-level item lands, because there is currently no supported way for the compiler to read
the current item inside a mapper. Do not attempt to fix the consumer from this repo.

## 2. Goal

After this change, an input or output mapper can see the execution pointer's `contextItem` and the
surrounding `StepExecutionContext`, and the fluent builders `.if()`, `.while()` and `.foreach()`
accept item-aware expressions. A workflow author can write a multi-step foreach body whose steps pass
data to each other, branch on the current item, and iterate a nested collection derived from that
item — without cross-iteration interference. Existing two-argument mappers continue to compile and
behave exactly as they do today.

## 3. Out of scope

- **Do not** change how `Foreach` fans out. Whole-collection branching stays as-is; batching,
  chunking and `maxConcurrency` are a separate future item.
- **Do not** introduce a per-scope or per-pointer *persisted* data object. This spec adds **read**
  access to `contextItem` in mappers; it does not partition `instance.data`. Partitioned scope data
  changes the at-rest format and must be its own spec.
- **Do not** modify any persistence, queue or lock provider. No core provider interface changes here.
- **Do not** change `ExecutionPointer`, `ContainerData`, or anything written to a provider.
- **Do not** alter the lockstep breadth-first execution order in `workflow-executor.ts:39`. It is
  load-bearing for `H1` bounded concurrency and `H2` lock-release ordering.
- **Do not** touch `core/src/primitives/container-step-body.ts` or `isBranchComplete`.
- **Do not** refactor `WorkflowExecutor.execute()` beyond the two mapper call sites.
- **Do not** rename `StepExecutionContext.item`.
- **Do not** edit files under `core/build/`, `node_modules/`, or `providers/*/build/`.

## 5. Interface & data-model changes

```ts
// BEFORE — core/src/models/workflow-step.ts:23-24
public inputs:  Array<(step: StepBody, data: any) => void> = [];
public outputs: Array<(step: StepBody, data: any) => void> = [];

// AFTER
public inputs:  Array<(step: StepBody, data: any, context?: StepExecutionContext) => void> = [];
public outputs: Array<(step: StepBody, data: any, context?: StepExecutionContext) => void> = [];
```

```ts
// BEFORE — core/src/services/workflow-executor.ts:85-87 and :127-129
for (let input of step.inputs) {
    input(body, instance.data);
}
...
for (let output of step.outputs) {
    output(body, instance.data);
}

// AFTER
for (let input of step.inputs) {
    input(body, instance.data, stepContext);
}
...
for (let output of step.outputs) {
    output(body, instance.data, stepContext);
}
```

```ts
// BEFORE — core/src/fluent-builders/step-builder.ts:81,86
public input(expression: (step: TStepBody, data: TData) => void): StepBuilder<TStepBody, TData>
public output(expression: (step: TStepBody, data: TData) => void): StepBuilder<TStepBody, TData>

// AFTER
public input(
    expression: (step: TStepBody, data: TData, context?: StepExecutionContext) => void
): StepBuilder<TStepBody, TData>

public output(
    expression: (step: TStepBody, data: TData, context?: StepExecutionContext) => void
): StepBuilder<TStepBody, TData>
```

```ts
// BEFORE — step-builder.ts:143, :158, :173
public foreach(expression: (data: TData) => any[]): StepBuilder<Foreach, TData> {
    newStep.inputs.push((step: Foreach, data: any) => step.collection = expression(data));

public while(expression: (data: TData) => boolean): StepBuilder<While, TData> {
    newStep.inputs.push((step: While, data: any) => step.condition = expression(data));

public if(expression: (data: TData) => boolean): StepBuilder<If, TData> {
    newStep.inputs.push((step: If, data: any) => step.condition = expression(data));

// AFTER — expression gains an optional second parameter carrying the enclosing item
public foreach(
    expression: (data: TData, item?: any) => any[]
): StepBuilder<Foreach, TData> {
    newStep.inputs.push((step: Foreach, data: any, context?: StepExecutionContext) =>
        step.collection = expression(data, context?.item));

public while(
    expression: (data: TData, item?: any) => boolean
): StepBuilder<While, TData> {
    newStep.inputs.push((step: While, data: any, context?: StepExecutionContext) =>
        step.condition = expression(data, context?.item));

public if(
    expression: (data: TData, item?: any) => boolean
): StepBuilder<If, TData> {
    newStep.inputs.push((step: If, data: any, context?: StepExecutionContext) =>
        step.condition = expression(data, context?.item));
```

> **Design decision, already made — do not revisit during implementation.** The third mapper
> parameter is the full `StepExecutionContext`, not a bare `item`. Rationale: mappers already need
> `pointer.id` and `workflow.id` for correlation in the consumer, and passing the context object
> costs nothing at the call site since it is already constructed at `workflow-executor.ts:76-81`.
> The *builder* expressions (`.if`/`.while`/`.foreach`) receive only `item`, because exposing the
> whole context there would invite predicate authors to mutate instance state from inside a
> condition.

> **Design decision, already made.** Output collision is resolved by *enabling* the caller to key
> writes by item (they now have `context.item` and `context.pointer.id`), **not** by partitioning
> `instance.data`. Partitioning is a persisted-format change and is explicitly out of scope (§3).

### DI / config impact

None. No change to `configureWorkflow()`, `WorkflowConfig`, or `TYPES` bindings. No new config
options.

### Persisted / at-rest format impact

**None.** `inputs` and `outputs` are code-side function arrays on `WorkflowStepBase`; they are never
serialised to a provider. `ExecutionPointer.contextItem` already exists and already persists — this
change only reads it. No migration, forward or backward.

## 6. Behavioural contract (numbered rules)

1. An `.input()` mapper registered on a step inside a `.foreach().do(...)` body receives, as its
   third argument, a `StepExecutionContext` whose `.item` strictly equals the collection element for
   that iteration.
2. An `.output()` mapper on such a step receives the same `StepExecutionContext` as its third
   argument, with the same `.item`.
3. For a step **outside** any container, the third argument is still a valid `StepExecutionContext`
   and `context.item` is `undefined`.
4. **Backward compatibility:** a mapper declared with two parameters is invoked unchanged and
   observes identical behaviour to before this change. No existing test may be modified to
   accommodate the new signature.
5. `.if(expr)` inside a foreach body evaluates `expr(data, item)` where `item` is the enclosing
   iteration's element. A predicate that returns `false` for a given item must skip that item's
   branch only, leaving other iterations unaffected.
6. `.while(expr)` inside a foreach body likewise receives the enclosing item as its second argument.
7. A nested `.foreach(expr)` inside a foreach body evaluates `expr(data, item)` and iterates the
   returned array. Inner-body steps receive the **inner** element as `context.item`; the outer
   element is not directly reachable from the inner mapper (callers who need it must capture it into
   `data` themselves, keyed per outer item).
8. **Ordering:** the change must not alter the number, order, or `active` state of pointers produced
   by any existing scenario. Pointer counts in existing tests remain identical.
9. **Idempotency:** re-running a pass over the same pointer set produces the same mapper arguments;
   `context.item` is read from the persisted `pointer.contextItem`, so it survives a host restart
   mid-body.
10. **Concurrency:** with two hosts processing the same instance under the existing distributed lock,
    a pointer's mapper always observes the `contextItem` belonging to that pointer, never another's.
11. **Error path:** if a mapper throws, behaviour is unchanged from today — the exception propagates
    to the existing `catch` at `workflow-executor.ts:74` and is handled by `handleStepException`.
    Mapper exceptions must not be swallowed or newly wrapped.

## 8. Test plan (TDD)

New file `core/spec/scenarios/foreach-scope-isolation.spec.ts`. Follow the arrangement in the
existing `core/spec/scenarios/` suites and use the `spinWaitCallback` helper to await completion.

### Failing-test-first

- **`multi-step foreach body isolates data between iterations`** — arrange: a workflow with
  `.foreach(d => d.items)` over `[1, 2, 3]` and a **two-step** body; step 1 has
  `.output((s, d, ctx) => { d.seen = d.seen || {}; d.seen[ctx.item] = ctx.item * 10; })`; step 2 has
  `.input((s, d, ctx) => s.value = d.seen[ctx.item])` and records `s.value` into a results array.
  Act: start the workflow, spin-wait for completion. Assert: the recorded values are exactly
  `[10, 20, 30]` in some order. **Before the fix this test cannot even be written against the public
  API (the mapper has no third parameter), and the two-parameter equivalent — writing to a single
  `d.value` slot — yields `[30, 30, 30]`.** Include that two-parameter variant as a documented
  regression witness in the same file, asserting the corrupted result, with a comment explaining it
  demonstrates the pre-fix behaviour and must be deleted only if the shared-sink semantics change.
  Proves §6.1, §6.2.

### Coverage

- **`context.item is undefined outside a container`** — a flat two-step workflow; assert both mappers
  receive a defined `context` and `context.item === undefined`. Proves §6.3.
- **`two-parameter mappers keep working`** — an existing-style workflow using only `(step, data)`
  mappers; assert unchanged results. Proves §6.4.
- **`if inside foreach branches per item`** — `.foreach(d => d.items)` over `[1,2,3,4]` with
  `.if((d, item) => item % 2 === 0)` guarding a recording step; assert only `2` and `4` were
  recorded. Proves §6.5.
- **`while inside foreach sees the item`** — assert the loop condition receives the enclosing item.
  Proves §6.6.
- **`nested foreach iterates a collection derived from the outer item`** — outer over
  `[{id:'a', lines:[1,2]}, {id:'b', lines:[3]}]` with `.foreach((d, item) => item.lines)`; assert the
  inner body observed `context.item` values `[1, 2, 3]`. Proves §6.7.
- **`pointer counts are unchanged`** — run an existing foreach scenario and assert
  `instance.executionPointers.length` matches the pre-change value. Proves §6.8.
- **`contextItem survives a host restart mid-body`** — persist with the memory provider, stop the
  host after pass 1, restart, complete; assert per-item isolation held. Proves §6.9.
- **`mapper exceptions still route to handleStepException`** — a mapper that throws; assert the
  existing retry/error behaviour is unchanged. Proves §6.11.
- **`saga compensation inside foreach sees its own item`** — a `.saga()` body inside a foreach whose
  compensation mapper reads `ctx.item`; assert each compensation observed its own element. Guards the
  `buildCompensationPointer` path (`execution-pointer-factory.ts:57` already propagates
  `contextItem`). Proves §6.1 on the compensation path.

## 10. Backward compatibility & migration

**Public API: additive, non-breaking.** Adding a third optional parameter to the mapper function type
is safe in both directions:

- **Runtime:** JavaScript ignores surplus arguments, so every existing two-parameter mapper continues
  to execute identically.
- **TypeScript:** a function of type `(step, data) => void` is assignable to
  `(step, data, context?) => void` — fewer parameters is assignable to more. Existing consumer code
  compiles unchanged.

**At-rest format:** unchanged. No migration required. Instances persisted by an older version resume
correctly on the new version and vice versa.

**Version bump: MINOR** — `2.5.0` → `2.6.0`. Additive public API, no breaking change, no prerelease
suffix (per strict semver, `UPGRADES.md`).

**Consumer impact (`reactory-express-server`):** none forced. The server integrates via the
`file:./lib/workflow-es/reactorynet-workflow-es-<version>.tgz` dependency and will keep building
without change. It *unblocks* the corresponding YamlFlow fix in that repository, which should be
scheduled immediately after this lands and will require the version bump plus a re-pack via
`bin/install.sh`. Note in the release notes that the YamlFlow `stepResults` collision is **not**
fixed by this change alone.

## 11. Definition of Done

Input and output mappers receive the executing pointer's `StepExecutionContext` — and therefore its
`contextItem` — as an optional third argument, and the `.if()`, `.while()` and `.foreach()` builder
expressions receive the enclosing iteration's item as an optional second argument. A multi-step
foreach body can pass data between its steps, branch on the current row, and iterate a nested
collection derived from that row, with each iteration observing only its own data. Every existing
two-parameter mapper behaves exactly as before, no existing spec required modification, no provider
changed, and nothing new is written at rest. The regression witness test documents the pre-fix
corruption so the guarantee cannot silently regress.

## 12. Implementation notes (optional, non-binding)

- Suggested edit order: (1) widen the type in `workflow-step.ts`; (2) pass `stepContext` at the two
  call sites in `workflow-executor.ts`; (3) write the failing test and watch it fail; (4) widen
  `.input()`/`.output()`; (5) make `.if()`/`.while()`/`.foreach()` item-aware; (6) remaining tests.
- `stepContext` is already fully constructed at `workflow-executor.ts:76-81` before the inputs loop
  at `:85`, so no reordering is needed for the input call site. Confirm the same for outputs at
  `:127` — `stepContext` is still in scope there.
- `StepExecutionContext` is declared in `core/src/models/step-execution-context.ts` and has exactly
  five fields (`workflow`, `step`, `pointer`, `persistenceData`, `item`). Import it into
  `workflow-step.ts` and `step-builder.ts`; watch for a circular import between `models/` and
  `fluent-builders/` — if one appears, use a `import type { ... }` type-only import.
- Upstream equivalent: `danielgerlag/workflow-es` has the same two-parameter mapper contract and the
  same limitation. There is no upstream patch to port; this is a fork-local improvement. Keep the
  change small enough that a future upstream merge stays tractable.
- The `If` primitive branches with `ExecutionResult.branch([null], containerData)`
  (`core/src/primitives/if.ts:16`), so a pointer created under an `if` inside a `foreach` gets
  `contextItem = null`, not the outer item. `buildNextPointer` propagation does not help here because
  the child pointer comes from `buildChildPointer` with `branch = null`. **Verify this during
  implementation** — if `if`-nested-in-`foreach` bodies lose the item, either propagate the parent's
  `contextItem` when the branch value is `null`, or document the limitation explicitly and add a test
  asserting the documented behaviour. Do not leave it undefined and untested.
