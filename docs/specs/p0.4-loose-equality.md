## 1. Context (self-contained)

Three locations in the codebase use loose equality (`==`) or falsy checks on numeric enums where strict comparison (`===` or explicit null-check) is required:

### Site 1 — Outcome value matching (execution-result-processor.ts:55)

```typescript
for (let outcome of step.outcomes.filter(x => 
    (x.value(instance.data) == stepResult.outcomeValue) || (x.value(instance.data) == null))) {
```

`==` means `1 == true`, `"0" == 0`, `"" == 0` all match. Two different values that coerce to the same type can produce unexpected outcome matches, causing the wrong branch or next-pointer to be created. The `== null` variant is intentional (matches both `null` and `undefined`) but should use explicit checks for clarity: `(x.value(instance.data) === null || x.value(instance.data) === undefined)` → `x.value(instance.data) == null` is acceptable here if the intent is "nullish", but should be documented.

**Fix:** Replace `== stepResult.outcomeValue` with `=== stepResult.outcomeValue`. Keep `== null` for the nullish check (it intentionally matches both `null` and `undefined`).

### Site 2 — Event key comparison (event-queue-worker.ts:206)

```typescript
let pointers = workflow.executionPointers.filter(p => 
    p.eventName == sub.eventName && p.eventKey == sub.eventKey && !p.eventPublished);
```

`p.eventKey` is typed `any`; `sub.eventKey` is typed `string`. Loose equality means a string `"1"` could match the number `1`, causing cross-tenant or cross-key event subscription matches. 

**Fix:** Replace with `===` for both comparisons, and add explicit type handling if needed:
```typescript
p.eventName === sub.eventName && String(p.eventKey) === String(sub.eventKey) && !p.eventPublished
```

### Site 3 — Error behavior falsy check (execution-result-processor.ts:73)

```typescript
let errorOption = step.errorBehavior;
if (!errorOption) {
    if (this.shouldCompensate(workflow, definition, pointer))
        errorOption = WorkflowErrorHandling.Compensate;
    else
        errorOption = definition.errorBehavior;
}
```

`!0 === true`. If `step.errorBehavior` is set to `0` (which maps to `ExecutionPipelineDirective.Next` or a no-op sentinel), the falsy check triggers and overrides with the default — an incorrect fallback. **Fix:** Replace with explicit null/undefined checks: `if (errorOption === undefined || errorOption === null)`

## 2. Goal

Replace all three loose-equality/falsy-check comparisons with strict comparisons that correctly distinguish between zero/sentinel values and "not set." No behavioral change for existing correct usage; fixes subtle bugs where coercion could produce unexpected matches.

## 6. Behavioural contract (numbered rules)

1. Outcome value matching uses `===` (strict equality), not `==`. The nullish check (`x.value(instance.data) == null`) is preserved for its intended "match both null and undefined" semantics.
2. Event key comparison uses `===` with explicit string coercion on both sides: `String(p.eventKey) === String(sub.eventKey)`. This ensures type-safe matching regardless of the original types, without allowing `1 == "1"`-style coercion surprises.
3. Error behavior check uses `errorOption === undefined || errorOption === null` instead of `!errorOption`, correctly treating `0` as a valid explicit value rather than "not set."

## 12. Implementation notes (optional, non-binding)

For site 2, use `String(p.eventKey) === String(sub.eventKey)` — this handles any input type safely. If performance is a concern for high-throughput scenarios, consider an early return for same-type values (`typeof p.eventKey === typeof sub.eventKey && p.eventKey === sub.eventKey`) before falling back to string coercion, but that adds complexity without clear benefit for this codebase.
