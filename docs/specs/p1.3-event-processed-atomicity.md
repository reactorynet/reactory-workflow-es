> ## 🛑 VERIFICATION CORRECTION (2026-06-27) — REJECTED, AND THE PROPOSED FIX IS A REGRESSION
>
> Re-checked against the code: the described bug **does not exist**, and implementing the fix as written would **make the engine
> worse**. Do not implement.
>
> **Why there is no bug.** Re-seeding is already prevented by two mechanisms in `seedSubscription`/`processEvent`:
> 1. Each successful `seedSubscription` calls `await self.persistence.terminateSubscription(sub.id)` (`event-queue-worker.ts:217`).
>    That removes the subscription, so a re-read of the event returns only the *not-yet-seeded* subscriptions — a per-subscription
>    checkpoint that makes a crash **resumable without duplication**.
> 2. The pointer filter `!p.eventPublished` (`:206`) plus `p.eventPublished = true` (`:209`) stops the same pointer being seeded
>    twice even if a subscription were reprocessed.
>
> The audit's own acceptance ("mark each subscription as seeded before processing the next") is therefore **already implemented**.
>
> **Why the proposed fix is harmful.** Calling `markEventProcessed` *unconditionally before* the loop (§2, §6.2, §12) means any
> subscription that is transiently locked (`acquireLock` returns false) or throws is **never retried** — the event is already
> marked processed and will not be re-polled. This converts today's correct *at-least-once-with-idempotency* delivery into lossy
> *best-effort*, and would cause the very "missed delivery" class of bug the audit was trying to prevent.
>
> **Action:** keep the current ordering (`markEventProcessed` after a fully-successful seed loop). Original text retained below for
> traceability only.

## 1. Context (self-contained)

### The bug

In `core/src/services/event-queue-worker.ts:seedSubscription`, the event seeding loop:

```typescript
// event-queue-worker.ts, lines ~175-179
let success = true;

for (let sub of subs)
    success = success && await self.seedSubscription(self, evt, sub);

if (success)
    await self.persistence.markEventProcessed(eventId);
```

`markEventProcessed` is called **after** all subscription seeding completes. If a node crashes between seeding the last subscription and marking the event as processed:
1. The event remains unprocessed in the persistence store
2. Another node reads the same event on its next tick
3. It seeds the same subscriptions again (duplicate execution)

This violates the at-most-once guarantee for event seeding. The lock acquisition prevents concurrent processing of the *same event*, but a crash within the seed loop is not protected by any lock (the event lock covers this node's processing, but not persistence durability).

### Impact

Event-driven workflows can double-execute on crash recovery. If an event triggers order processing and the node crashes after shipping 2 out of 3 subscriptions, a restart ships all 3 again — duplicate orders.

---

## 2. Goal

Move `markEventProcessed` to **before** the subscription seed loop (or per-subscription). This ensures the event is marked processed before any mutation happens, making it safe against crash mid-seed:
- If a crash occurs, the event is already marked processed — no re-processing.
- Partial seeding means some workflows miss the event data — acceptable trade-off (events are fire-and-forget delivery semantics).

The recommended approach: mark processed **before** the loop starts, with a comment documenting that partial seeding is an accepted consequence of this design choice.

## 6. Behavioural contract (numbered rules)

1. `markEventProcessed(eventId)` must be called **before** iterating the subscription seed loop — not after.
2. The `success` flag and conditional `markEventProcessed` is removed; the event is always marked processed unconditionally before seeding begins.
3. If any individual subscription seed fails, it logs the error and continues to subsequent subscriptions — no early termination of the loop.
4. A comment documents that partial seeding (some workflows receive the event, others do not after a crash) is an accepted consequence of this design choice.

## 10. Backward compatibility & migration

No public API change. The behavioral change (event marked processed earlier) means workflows that previously would have been re-seeded after a crash will NOT be re-seeded — this is the correct behavior, but consumers relying on the buggy "re-seed everything" behavior may see different outcomes. This is not a regression; it fixes incorrect semantics.

## 12. Implementation notes (optional, non-binding)

The change is minimal:
```typescript
// BEFORE: after loop
for (let sub of subs)
    success = success && await self.seedSubscription(self, evt, sub);
if (success)
    await self.persistence.markEventProcessed(eventId);

// AFTER: before loop
await self.persistence.markEventProcessed(eventId);  // Mark first — partial seeding is acceptable trade-off for crash safety
let success = true;
for (let sub of subs) {
    try {
        const ok = await self.seedSubscription(self, evt, sub);
        success = success && ok;
    } catch (err) {
        // Log but continue to remaining subscriptions
    }
}
```
